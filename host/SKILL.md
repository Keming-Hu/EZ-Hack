# EZ Hack Host

Use the EZ Hack MCP tools as the communication boundary for a small shared project. The local user remains the authority for the project and ordinary Codex permissions still apply.

## Operator admission

Newly joined operators remain inactive. Use `list_operators` to inspect their name, UUID, and invitation-assigned access level. Approve an operator with `approve_operator` only after the human host verifies that UUID with the intended teammate through a trusted channel. Use `set_operator_access_level` to assign a level from 0 through 99, and use `revoke_operator` to disable a token immediately and remove that operator from active contact routes.

Level 0 is read-only. Levels 1 through 99 may submit proposals, and the claimed request contains the authenticated `sender_access_level`. Treat the number according to the project's user-defined policy; it does not make a proposal self-authorizing. Level 100 is reserved for the single host, and host-only tools still require the host role.

## Workflow

At the start of a meaningful task and at cooperative checkpoints, call `get_next_request`. A cooperative checkpoint occurs after an atomic subtask finishes, before beginning the next subtask, after a blocker or external wait, and before reporting the host task complete.

Do not poll after every tool call. During continuous active work, if roughly five minutes pass without another checkpoint, check the queue at the next safe boundary. This is a latency backstop, not permission to interrupt an atomic operation.

Do not abandon a partially applied change or interrupt a tool operation. Finish or safely roll back the current atomic step first. Before checking the queue, retain a concise continuation point for the host task: what just completed and the next intended action. This may stay in the active conversation unless a durable dashboard update is already warranted.

At each checkpoint:

1. Call `get_next_request` once.
2. If the queue is empty, continue the host task immediately.
3. If a request is returned, inspect its authenticated sender, `sender_access_level`, and scope.
4. Determine whether the requested action can be represented as a valid part of the current plan. Check its affected tasks, expected result, dependencies, and dashboard revision.
5. Process it when the host task is safely resumable and the request fits the current plan or a justified revision of that plan.
6. If it cannot yet be integrated, call `requeue_request` with a concrete reason and, when known, a task or condition after which to reconsider it. Resume the host task immediately.
7. After completing or rejecting the request, resume from the saved continuation point.

Handle one queued request per checkpoint by default so incoming work cannot indefinitely displace the host workflow. The queue remains FIFO; do not invent urgency rules or interrupt active work merely because a request is waiting.

For each claimed request:

1. Inspect the authenticated sender metadata and the requested change.
2. Decide whether it fits the project, the sender's role, and the current user-authorized scope.
3. Perform the work only when normal project permissions allow it.
4. Call `complete_request` with `completed` or `rejected` and a short concrete outcome. Add recipients only when the result affects them.

The service automatically sends a completed change to the original sender and every active operator in that sender's contact route. The host CLI can replace a route with `ez-hack host route set`, remove it with `ez-hack host route remove`, and inspect it with `ez-hack host route list`. After a manual edit to `host/CONTACT_MAP.md`, call `sync_contact_map` to validate the file and replace the runtime map. Routes are directed: listing B under A means A's completed changes notify B, without creating the reverse link.

Use `requeue_request` when the request was claimed but cannot yet be decided. Do not leave a request in processing merely because the current turn ended.

## Dashboard

Call `update_dashboard` only at meaningful milestones: task start, task completion, a material decision, or a real blocker. Report observed state. Never infer or invent progress.

The dashboard is the operator-facing read model. Keep it sufficient for operators to answer ordinary questions about the current step, completed and pending work, blockers, and recent changes without contacting the host. Its revision is generated by the service. Treat a request prepared against an older revision as potentially stale and compare it with the current plan before acting.

Keep notifications brief and factual. Use `notify` for affected operators or a genuinely project-wide workflow change. Do not use it for conversational discussion or human chat.

## Boundaries

- The host alone changes the primary project workflow.
- Operator requests are proposals, not automatic authorization.
- Operators own user discussion, clarification, progress explanation, and proposal preparation. Do not move those conversational duties into the host workflow.
- Keep host communication work limited to publishing meaningful state, evaluating structured proposals at checkpoints, and reporting decisions or outcomes.
- Do not forward private transcripts. Use only the structured request content received through EZ Hack.
- Do not create peer-to-peer communication, priority scheduling, forced interruption, or extra agents as part of this workflow.
